    Navigation

    This template uses Jetpack Navigation 3, not navigation-compose. There is no navigation graph resource, no route strings, and no back-stack argument bundle — destinations are typed keys, and a small core/navigation module owns the state and the one class allowed to change it.

    Concepts

    Type What it does Where
    NavKey Marker for a destination. @Serializable, so it survives process death. one per destination, next to its feature's entries (e.g. HomeNavKey, ItemNavKey)
    NavigationState Holds one back stack per top-level destination, plus the order they were visited in. core/navigation/src/main/kotlin/dev/atick/core/navigation/NavigationState.kt
    Navigator The only thing that mutates NavigationState. core/navigation/src/main/kotlin/dev/atick/core/navigation/Navigator.kt
    NavDisplay Renders the flattened back stack. app/src/main/kotlin/dev/atick/compose/ui/JetpackApp.kt
    entry<T> / entryProvider Maps a NavKey type to a composable. per-feature navigation/*Navigation.kt files
    ListDetailSceneStrategy Adaptive list/detail layout for wide windows. JetpackApp.kt, feature/home/.../navigation/HomeNavigation.kt

    Defining a destination

    A destination with no argument is a data object; one with an argument is a data class:

    // feature/auth/src/main/kotlin/dev/atick/feature/auth/navigation/AuthNavigation.kt
@Serializable
data object SignInNavKey : NavKey

// feature/home/src/main/kotlin/dev/atick/feature/home/navigation/HomeNavigation.kt
@Serializable
data class ItemNavKey(val itemId: String?) : NavKey

    Registering entries

    Each feature module exposes an EntryProviderScope<NavKey> extension that registers its destinations. Metadata (like ListDetailSceneStrategy.listPane()) attaches per entry, not per graph:

    // feature/home/src/main/kotlin/dev/atick/feature/home/navigation/HomeNavigation.kt
fun EntryProviderScope<NavKey>.homeEntries(
    navigator: Navigator,
    onShowSnackbar: suspend (String, SnackbarAction, Throwable?) -> Boolean,
) {
    entry<HomeNavKey>(
        metadata = ListDetailSceneStrategy.listPane(),
    ) {
        HomeScreen(
            onJetpackClick = navigator::navigateToItem,
            onShowSnackbar = onShowSnackbar,
        )
    }

    entry<ItemNavKey>(
        metadata = ListDetailSceneStrategy.detailPane(),
    ) { key ->
        ItemScreen(
            itemId = key.itemId,
            onBackClick = navigator::goBack,
            onShowSnackbar = onShowSnackbar,
        )
    }
}

    The app module combines each feature's entries under one entryProvider { } per graph (see Wiring NavDisplay). Each feature also declares fun Navigator.navigateToX() extensions next to its keys, so the app can wire callbacks through that feature's public API. A feature should not depend on another feature to call its extension; cross-feature wiring belongs in the app:

    fun Navigator.navigateToItem(itemId: String?) = navigate(ItemNavKey(itemId))

    Multi-back-stack state

    rememberNavigationState builds one back stack per top-level destination (subStacks) plus a separate stack recording the order those destinations were visited (topLevelStack):

    // core/navigation/src/main/kotlin/dev/atick/core/navigation/NavigationState.kt
@Composable
fun rememberNavigationState(
    startKey: NavKey,
    topLevelKeys: Set<NavKey>,
): NavigationState {
    val topLevelStack = rememberNavBackStack(startKey)

    val subStacks = topLevelKeys.associateWith { topLevelKey ->
        key(topLevelKey) { rememberNavBackStack(topLevelKey) }
    }

    return remember(startKey, topLevelKeys) {
        NavigationState(
            startKey = startKey,
            topLevelStack = topLevelStack,
            subStacks = subStacks,
        )
    }
}

    Tip

    key(topLevelKey) is what gives each sub stack its own saved-state slot. Without it, every iteration of the associateWith lambda shares the composition's compound key hash, so all the stacks register under one key and are restored by position rather than by which destination they belong to — a tab can silently come back with another tab's history after process death. NavigationStateTest (see Testing) is the regression test for this.

    NavigationState derives the current tab and current screen from those two stacks, and never mutates itself — only Navigator does:

    class NavigationState(
    val startKey: NavKey,
    val topLevelStack: NavBackStack<NavKey>,
    val subStacks: Map<NavKey, NavBackStack<NavKey>>,
) {
    val currentTopLevelKey: NavKey by derivedStateOf { topLevelStack.last() }
    val topLevelKeys: Set<NavKey> get() = subStacks.keys
    val currentSubStack: NavBackStack<NavKey>
        get() = subStacks[currentTopLevelKey]
            ?: error("Sub stack for $currentTopLevelKey does not exist")
    val currentKey: NavKey by derivedStateOf { currentSubStack.last() }
}

    NavDisplay needs one flat list, not a map of stacks — the backStack extension property flattens them in visit order, which is also what makes back-from-another-tab return to the start tab rather than exiting the app:

    val NavigationState.backStack: List<NavKey>
    get() = topLevelStack.flatMap { subStacks[it].orEmpty() }

    The Navigator

    navigate(key) picks its behavior from what kind of destination key is:

    key is... Effect
    the current top-level destination pops its stack back to the root — "tap the selected tab again to go home"
    another top-level destination switches to it, preserving where the user was
    anything else pushes onto the current top-level destination's stack 
    // core/navigation/src/main/kotlin/dev/atick/core/navigation/Navigator.kt
fun navigate(key: NavKey) {
    when (key) {
        state.currentTopLevelKey -> clearSubStack()
        in state.topLevelKeys -> goToTopLevel(key)
        else -> goToKey(key)
    }
}

fun goBack() {
    when (state.currentKey) {
        state.startKey -> Unit
        state.currentTopLevelKey -> state.topLevelStack.removeLastOrNull()
        else -> state.currentSubStack.removeLastOrNull()
    }
}

fun canGoBack(): Boolean = state.currentKey != state.startKey

    Calling goBack() from the start key does nothing — there is nowhere left to go, and only the system back handler finishes the activity. A screen can wire a back button straight to navigator::goBack; use canGoBack() to decide whether to handle back at all (see Wiring NavDisplay).

    Entry identity and duplicate destinations

    Two identities matter in this template:

    • Navigator uses key equality when removing a destination from the current sub-stack before pushing it. ItemNavKey("a") and ItemNavKey("b") are different keys; navigating to "a" again moves that key to the top of this sub-stack. It does not remove an equal key from another tab.
    • Navigation 3's entry decorators use NavEntry.contentKey. In the pinned Navigation 3 1.1.4, its default is key.toString(), not the key object. The saveable-state decorator passes this value to SaveableStateProvider; lifecycle 2.11.0 uses it to select the ViewModel store owner.

    For these data-class keys, different item IDs produce different default content keys. Sharing a key type is therefore not itself a collision. Equal keys in two flattened tab stacks do collide; even unequal custom keys can collide if their toString() values are the same. The decorators associate state by content key, and simultaneous rendering of duplicate saveable-state keys can fail rather than produce two independent screens. The resolved Compose saveable-state 1.11.4 sources contain the duplicate-key check.

    Keep a nested destination owned by one top-level stack when following the existing design. If two tabs need independent instances of a shared screen, give them distinct destination keys (separate key types are one option) and verify their content keys differ. Do not resolve this by overriding toString() casually: identity must stay stable across restoration. An owner argument or custom content-key policy requires a separately reviewed navigation design and restoration tests.

    The version-specific behavior above was checked in the published Navigation 3 runtime sources and lifecycle decorator sources. Recheck this behavior when upgrading those dependencies.

    Wiring NavDisplay

    JetpackApp picks between two independent graphs based on appState.isUserLoggedIn. Each graph builds its own NavigationState. Changing between signed-in and signed-out UI removes the previous graph's composition; back in the new graph does not traverse the removed graph's navigation history:

    Graph Composable startKey topLevelKeys
    Signed-out SignedOutNavigation SignInNavKey setOf(SignInNavKey)
    Signed-in SignedInNavigation TopLevelDestination.START.key TopLevelDestination.keys

    These are navigation boundaries, not data authorization or a complete account-reset protocol. A direct account change that leaves isUserLoggedIn true does not itself select another graph. Repositories, cached preferences and pending sync work need their own account handling.

    The signed-in setup uses the enum's keys; the signed-out setup supplies SignInNavKey instead:

    val navigationState = rememberNavigationState(
    startKey = TopLevelDestination.START.key,
    topLevelKeys = TopLevelDestination.keys,
)
val navigator = remember(navigationState) { Navigator(navigationState) }

    NavDisplay renders the flattened backStack, and each entry gets its saved state and ViewModelStore from rememberDefaultEntryDecorators():

    // app/src/main/kotlin/dev/atick/compose/ui/JetpackApp.kt
NavDisplay(
    backStack = navigationState.backStack,
    entryDecorators = rememberDefaultEntryDecorators(),
    sceneStrategies = listOf(rememberListDetailSceneStrategy<NavKey>()),
    onBack = navigator::goBack,
    entryProvider = entryProvider {
        homeEntries(navigator, onShowSnackbar)
        profileEntries(onShowSnackbar)
    },
)

    entryDecorators comes from core/navigation:

    @Composable
fun rememberDefaultEntryDecorators(): List<NavEntryDecorator<NavKey>> = listOf(
    rememberSaveableStateHolderNavEntryDecorator(),
    rememberViewModelStoreNavEntryDecorator(),
)

    NavDisplay installs its own back handler, but only while the current scene has entries behind it. The two-pane list-detail scene (see below) has the list and detail as one scene with nothing behind it, so the app also wires an explicit handler next to every NavDisplay:

    BackHandler(enabled = navigator.canGoBack()) { navigator.goBack() }

    Add a destination to the app

    1. Add the approved feature module as an app dependency, or keep the destination in its existing feature module. Expose its keys and entry-registration function publicly; the Screen can remain internal because the registration function calls it within that module.
    2. Import and call that registration function inside the appropriate entryProvider in JetpackApp.kt: signed-out for authentication, signed-in for authenticated screens. Every key that can be pushed in that graph needs a matching entry. Do not register one key type twice.
    3. For a tab, add an entry to app/.../navigation/TopLevelDestination.kt with its root key, selected and unselected icons, and app string resources for label/title. keys derives from enum entries; bar/rail items iterate those entries. Keep START pointing at the intended exit destination.
    4. Wire list clicks to the feature's navigator extension with an ID, and a create action with null if following Item's create/edit convention. Home's create FAB is explicitly conditional on the current top-level key in JetpackApp.kt; another tab's create action needs its own condition and callback. Registering a tab does not supply that action automatically.
    5. Preserve the existing decorators, scene strategy and explicit BackHandler. Verify switching tabs preserves each sub-stack, selecting the current tab pops to its root, and back from another tab's root follows top-level history. Returning to the start tab clears that history; back at the start key is left to the system.

    A screen pushed only inside a tab does not need a TopLevelDestination enum entry. Follow the feature guide for model, DI, resources, and testing steps.

    Adaptive list-detail

    The signed-in NavDisplay installs rememberListDetailSceneStrategy<NavKey>(). An entry opts into it with pane metadata — HomeNavKey is the list pane, ItemNavKey is the detail pane (both registered in homeEntries, shown under Registering entries). On a wide window the two render side by side; on a phone they behave as separate screens, and which layout applies is decided entirely by the scene strategy, not by the entries themselves.

    One consequence: on a wide window the list pane is still on screen beside the detail, but the last key in the back stack is the detail key. JetpackApp.kt tracks this explicitly rather than guessing from window size, since guessing wrong stacks two top app bars on what should be a single full-screen destination:

    val isAtTopLevel = navigationState.currentKey == navigationState.currentTopLevelKey

    Passing arguments to ViewModels

    This template carries destination arguments on the NavKey itself and explicitly supplies them to the factory; it does not decode those arguments from a SavedStateHandle. The argument reaches the ViewModel through Hilt's assisted-injection support, using ItemNavKey.itemId as the example end to end:

    1. The key carries the argument: 
      data class ItemNavKey(val itemId: String?) : NavKey
    2. The entry reads it off the key and passes it to the composable: 
      entry<ItemNavKey>(metadata = ListDetailSceneStrategy.detailPane()) { key ->
    ItemScreen(itemId = key.itemId, onBackClick = navigator::goBack, onShowSnackbar = onShowSnackbar)
}
    3. The composable requests the ViewModel with a creationCallback: 
      // feature/home/src/main/kotlin/dev/atick/feature/home/ui/item/ItemScreen.kt
itemViewModel: ItemViewModel = hiltViewModel<ItemViewModel, ItemViewModel.Factory>(
    creationCallback = { factory -> factory.create(itemId) },
),
    4. The ViewModel takes the argument through an @AssistedInject constructor: 
      // feature/home/src/main/kotlin/dev/atick/feature/home/ui/item/ItemViewModel.kt
@HiltViewModel(assistedFactory = ItemViewModel.Factory::class)
class ItemViewModel @AssistedInject constructor(
    private val homeRepository: HomeRepository,
    @Assisted private val existingJetpackId: String?,
) : ViewModel() {

    @AssistedFactory
    interface Factory {
        fun create(existingJetpackId: String?): ItemViewModel
    }
    // ...
}

    Use kotlinx.serialization.Serializable on the real key declaration (as shown under Defining a destination); the abbreviated declaration in step 1 omits it. The Screen uses androidx.hilt.lifecycle.viewmodel.compose.hiltViewModel; factory annotations come from dagger.assisted, and HiltViewModel from dagger.hilt.android.lifecycle.

    Every destination that needs a keyed argument in its ViewModel follows this four-step chain. The entry's ViewModel store retains an existing ViewModel; the creation callback supplies arguments when that instance is first created. It is not a mechanism for updating an existing ViewModel's arguments. Put identity-bearing arguments on the key and test restoration with two different IDs.

    Testing

    core/navigation's own test suite covers this module directly — NavigatorTest builds a NavigationState by hand and exercises navigate()/goBack()'s branches, while NavigationStateTest drives an actual save/restore cycle with StateRestorationTester to guard the key() behavior described under Multi-back-stack state. See core/navigation/src/test/kotlin/dev/atick/core/navigation/ for both. Run:

    ./gradlew :core:navigation:testDebugUnitTest :feature:home:testDebugUnitTest

    When adding a destination, test equal-key re-navigation, distinct argument keys, top-level history, and restoration. If extending cross-tab identity, include a real decorated NavDisplay test; NavigatorTest alone does not exercise saveable-state or ViewModel-store collisions. On a device, check system and toolbar back in narrow/wide layouts and sign-in/sign-out graph changes.
